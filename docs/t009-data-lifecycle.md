# Account data lifecycle qualification

## Synthetic qualification and operational contracts

`privacy/personal-data-lifecycle.integration.test.ts` seeds every inventory class and two owners, exports the safe graph and erases the accepted owner through the restricted worker. It verifies RESTRICT edges, append-only accounting, no-FK credentials, orphan files, unrelated-owner preservation and global keys/budgets. `account_deletion` is naturally absent from the active snapshot and asserted during erasure. Globally referenced OAuth clients are disabled and stripped of owner references/secrets while unrelated consent survives.

The schema-enumerated column whitelist is authoritative. Credentials, proof capabilities, provider secrets, leases and restricted replay/audit material are excluded. Deleted/expired history is not reconstructed. `AccountSnapshotV1.unavailable` supports `NOT_RETAINED` but currently returns an empty array when no absent historical category can be established; it does not invent past availability.

File inventory combines registered metadata, actual application/agent/resume references and storage listing. Known missing/unreadable references fail preparation; paths remain owner-scoped and remote URLs are not fetched. Revoked but retained personal objects remain inventoried; explicitly removed `purpose=deleted` objects are excluded and purged through durable work. Legacy picture adoption requires an actual bounded user/resume reference and byte digest; unknown or revoked paths are denied.

New writes record intent before storage and recheck active admission before publication. Writes crossing deletion are compensated. Interrupted `ioPending` work stays blocked until actual settlement: internal `storage/ownership.ts::reconcileOwnedFileWrite({userId,key,confirmSettled})` accepts injected `settled|pending` evidence, preserves a published object or schedules unpublished compensation. Elapsed time is insufficient. There is no public recovery route or automatic production adapter settlement proof; authorized adapter/operator evidence is required before clearing a blocked write.

Deletion revokes sessions/proofs, blocks new work and late personal publication, drains leases and preserves cost/token/outcome accounting without result content/provider response IDs. Held scripted email/archive tests cross the barrier; separate held career/agent tests prove actual restricted SQL publication fencing, not whole provider transports. Completion waits on storage, active erasure and applicable external stages.

T010 implements `DeletionHooks.stopRenewals({requestId,userId})` → `not_applicable|confirmed|pending`; pending cannot complete. `ProcessorDeletionAdapter.erase({requestId,processor,subjectReference})` returns confirmed/pending plus optional receiptRef. Missing/unapproved adapters are never called and remain pending. Real processor approvals/history are not supplied by synthetic tests.

T012 reads ordered `DeletionReplayRecordV1` via `readDeletionRecords({afterSequence,limit})` (limit 1–1000), using a separately authorized recovery connection. Records include sequence/request/subject IDs, storage scopes, timestamps, stages, policyVersion and enumerated policy-reference exceptions; no CV, email, credential or raw provider/message payload. Runtime cannot read/mutate replay or operator audit. Restricted reader privileges are tested; no HTTP route exists. Independent preservation and restore/replay remain T012 work.

Synthetic retention durations are fixtures. Production backup/legal/support/tombstone policies, operator access and processor contracts remain gated. Active erasure proves neither backup destruction nor permission for real-data activation. See `t009-account-data-controls-evidence.md` for commands, logs and failures.
