## 2. Access and frame selection

Use your own authorized Figma connection to read the mapped frame, current render, components and variables. Links do not grant access. Never store credentials here or claim visual verification without inspecting the target.

Use `fileKey` plus the colon-separated `nodeId` in the map. Human links use `?node-id=123-456`; the corresponding API node ID is `123:456`. Verify the returned node name matches the map. If it was deleted, renamed or materially revised, refresh the registry and record the change; do not invent a replacement ID.

**Interface language is not document language.** Masters are Arabic-interface; the _English (LTR)_ masters (`secondLocale` on each screen in the map) show the English interface. `S08 · Editor: English document` and the English version on S21 explicitly demonstrate an English CV inside the Arabic interface; `S21 · Language versions: reviewing translation` changes only the English copy. The base editor can contain an Arabic CV even with English interface labels. Do not translate CV data when switching the interface.

**State is not route.** A pending, failed, verified or accepted Figma frame can be a state of one page/component. Do not create one app route, database table or service per frame. Prototype-only frames (`Popup · Simulator…`, `Popup · Note…`) are review tools, not product features. State masters are named `Sxx · Screen: state`; form dialogs (`Dialog · …` on desktop, `Sheet · …` on mobile) are the content of modal forms on their screen, not routes. Error specimens should result from real application state, not customer-facing “simulate error” buttons.

The published registry contains S01–S39 plus S08b. Use exact mapped baselines; new recovery additions in [OTP spec](specs/otp-spec.md) await publication with empty spec nodeIds. Phase 1 includes verified-mobile SMS reset/recovery codes; SMS-only sign-in stays Phase 2 off. A14-A16 evidence is still required.

## 4. How to implement a task

**Interface copy:** [copy-deck.json](copy-deck.json) is the single source of Arabic (`ar-SA`) and English (`en-US`) UI strings. English (LTR) masters show layout for key screens; other screens use Dir=LTR component variants, the Type collection in English mode and the copy deck. Arabic is authoritative for meaning; English copy is a proposal pending owner review. Semantic entries carry Lingui identities; the surface/channel indexes reference those entries. Interface language never translates or overwrites saved CV content.

1. **Scope it.** Identify its existing B-C/B-O requirements and A release criteria. Read relevant security/AI/architecture decisions. Keep employer B2B and other deferred features out unless separately approved.
2. **Inspect it.** Read the target and adjacent success/error/empty states from the map, then fetch current Figma context and a render. Check Arabic and English, desktop and mobile. Read existing code before proposing new components. Inventory the mapped shell, page, dialog, sheet and recovery-state elements before implementation. Render only the approved elements and exact icons/copy/order; do not retain an upstream action solely because it exists. Implement required behavior through shared components, not new lookalike controls. Record any requirement-driven exception and its decision.
3. **Reuse it.** Adapt the current React/Vite/TanStack Router frontend, shared UI and Hono/service layer. Map tokens through their semantic names. Do not paste generated absolute-positioned UI wholesale or replace the maintained app with the earlier HTML prototype. Build screens from existing shared components and shared layout APIs; reuse AppShell/PageHeader for dashboard pages. Keep padding, sidebar geometry, typography, radii and control sizes in their shared owners.
4. **Make it real.** Bind controls to validated state and services. “Saved” needs acknowledged persistence; accepted suggestions need revision checks and undo/history; payment access needs verified server state. Prototype variables, static dates, example card data and success messages are not implementations.
5. **Verify it.** Run the repository's actual type/lint/test commands and browser checks. Check key interactions, focus, errors, navigation and data integrity. For every changed screen and every dialog/state it touches, save a fresh Figma render and an app capture of the same target at the same size (Arabic always; English where an English master exists; desktop 1440 and mobile 390), using the correct fonts. Compare for D35 defects: missing, extra or wrong elements, icons, wording or order; broken layout, overflow or RTL; and brand distortion. Record each defect as fixed or intentional with its decision/release-gate reason and identify anything blocked. Spacing, sizes, radii and density follow shared code components; pixel parity is not required. Differences from Figma geometry are allowed; inconsistent geometry within the app is a defect, not deferred brand polish. A target without this record is not visually verified, regardless of passing tests. Use icons exactly as named in [icons.json](icons.json). Reject newly added raw UI font/color/spacing/radius values and control-size overrides outside shared definitions; require semantic roles and shared variants. Verify equal header/body start edges and invariant sidebar width across dashboard routes, matching toolbar heights, full select-label fit and avatar inset. Check AR/EN, narrow/wide layouts and every changed dialog/state; record evidence separately from functional smoke. Never create or update a screenshot baseline just to turn a failing test green, and never mask disputed regions (logo, language control); a baseline is valid only after a reviewed comparison.
6. **Document it.** Include requirement IDs, Figma node links, chosen commit, before/after screenshots and actual tests in the change/PR record. Update the authoritative document when behavior changes; update the map when a design target changes.
   Reject newly added raw UI font/color/spacing/radius values and control-size overrides outside shared definitions; require semantic roles and shared variants. Verify equal header/body start edges and invariant sidebar width across dashboard routes, matching toolbar heights, full select-label fit and avatar inset. Check AR/EN, narrow/wide layouts and every changed dialog/state; record evidence separately from functional smoke.

7. **Review feedback against the design.** A review comment reporting a D35 defect against the live Figma target or this documentation is a defect to fix, not a scope question. Spacing/size differences from Figma alone are not defects under D35; inconsistent app geometry is a defect. "Final owner approval open" (for example D11 brand) does not excuse a missing working logo, wrong icon or brand distortion. Decline a D35 defect only with an owner decision that says otherwise.

Do not expand the scope merely to perfect unrelated components. A connected primary journey matters more than the number of generated screens. Start with **import/manual facts → review → edit → save/reopen → export**, including Arabic and mixed-direction critical fields, before broad paid-product rollout.

### Accessibility contract

Apply this contract in code and verify it in the application; these are requirements, not implemented or tested behavior.

- Use exactly one H1 per screen: its screen title. Use H2 for sections and H3 for subsections; do not skip levels or choose headings for visual size. Keep CV preview headings subordinate to the screen H1.
- Use `header`/banner for the shell header, labelled `nav` regions for navigation, one `main` for the screen task, labelled `aside` regions for editor panels, and `footer`/contentinfo for the shell footer where present. Give modal dialogs and sheets `role="dialog"`, `aria-modal="true"` and `aria-labelledby` pointing to their visible title.
- Keep DOM, reading and keyboard focus order logical in both directions; do not reverse tab order merely because the UI is RTL or use positive `tabindex`. In S08, follow header controls, the editing panel on the right, then preview controls on the left; on mobile, enter only the active Write/Preview pane. In S11, follow original, proposal and decision actions; stack them in that order on mobile. Isolate LTR contact values without changing focus order.
- Move focus into an opened dialog/sheet, contain Tab/Shift+Tab within it, support Escape where dismissal is allowed, and make background content inert. Return focus to its trigger on close; if the action removed that trigger, move focus to the nearest logical surviving control.
- Give every icon-only button an accessible action name and target where needed (for example, document options or close dialog). Hide decorative icons from assistive technology; do not rely on an icon or tooltip alone.
- Announce toasts through a polite live region (`role="status"`); retain critical feedback inline too. Announce form errors assertively (`role="alert"`), save-status changes politely, and payment/export pending-stage updates politely. Announce meaningful changes once without moving focus or repeating every progress tick; never announce success before service confirmation.
- On invalid submit, show an error summary at the top of the form, focus it, and link each entry to its field. Retain entered values; link inline messages with `aria-describedby` and set `aria-invalid="true"` on invalid fields. Coordinate assertive announcements with summary focus to avoid duplicate speech.
- Respect `prefers-reduced-motion`: remove nonessential movement and use instant or near-instant transitions; preserve pending/status information in text. Do not animate document reflow.

Visual tradeoffs and scoped audit dispositions were reviewed. Application accessibility still requires testing.
